## 问题与目标行为

账号“按 IP 分组配置”和业务分组“同时为账号配置所选 IP 分组”会把完整 IP 池保存为候选绑定。旧实现仍沿用每 IP 的 `max_accounts`，使同池的后备账号在保存时因账号数量上限被拒绝，无法参与既有的优先级递补。

两处入口现在通过同一分配路径复制候选项，将所选 IP 的全局 `max_accounts` 持久化为0（不限）。全部目标账号都可绑定完整候选池，实际请求仍按每 IP 全局并发、账号总并发及已启用的严格优先级策略使用出口。这是代理的全局设置，其他绑定这些 IP 的账号也受影响；中英文界面明确说明这一点。

启用严格策略时仍按账号已有 Priority 升序、同值 ID 升序分配互不重叠的 IP 子集，不修改原 priority，也不要求手动逐个编号。账号总并发100、每IP并发10时，每账号使用10个IP：10个IP由优先账号使用，其余账号保留候选资格并按顺序接替；30个IP可供前三个账号各用不同的10个IP同时调用。用户已明确确认这一10IP/3账号依次使用、30IP/3账号各10IP并行的规则。子集并发满时等待或返回繁忙，不能借用其他子集；账号不可调度后仍须等待旧请求排空才能交接IP。

## 实施范围与保留边界

- 后端仅修改 `backend/internal/repository/account_proxy_group_assignment.go` 的共享分配路径 `assignWholeProxyGroup`：在原事务内复制分配项、将 `MaxAccounts` 置0，再交给原 `persistProxyAssignments` 保存。每IP并发和可选账号总并发仍与绑定同事务生效，失败整批回滚。
- 账号弹窗按“空闲代理”或“IP分组”模式显示相应说明，按组模式将数量标签改为“本次候选绑定数”。业务分组提示与容量示例同步中英文，说明绑定候选池不会自动启用业务分组严格策略，候选绑定数不代表同时使用数。
- 普通按空闲代理分配、单/批手动编辑、旧写入和授权入口保留原容量校验，并读取当前全局设置；本次不把0限额规则扩大到这些入口。影子继承、管理员边界、无效/到期代理拒绝、最多100个代理、保存失败保留草稿保持。
- 保留完整候选池、全局IP并发、账号总并发、HTTP/WS/Live及续链的原调度约束、租约排空和跨业务组物理互斥。没有修改运行时分片或请求转发逻辑。
- 无新增请求参数、迁移或依赖；旧迁移、历史用量、首字计时、账务和真实授权流程保持。没有后台批改历史配置，只有明确执行这两种配置操作时才保存所选IP的全局不限账号数设置。
