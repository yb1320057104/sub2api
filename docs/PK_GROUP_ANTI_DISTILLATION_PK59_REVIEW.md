# PK-048 分组防蒸馏保护移植记录

## 规则和使用

1. 后台 → 分组 → 编辑 OpenAI 分组 → 分组防蒸馏保护。可独立保存，默认关闭，暂停默认 5 分钟，可设 1～1440 分钟。新建分组后再编辑配置。
2. 按本站客户 `user_id` 合并多把 API Key 在已开启保护的 OpenAI 分组上的有效文本请求。按完成顺序保存最近 20 个样本，至少 18 个明确报告缓存读取为零时触发。不同分组配置不同时，触发样本所在分组的暂停时长生效。
3. 原始缓存数量缺失、无效、失败或未完成、已知客户端断连、图片/音视频以及 `previous_response_id` 等未展开历史引用不采样。普通 session/cache identity 本身不被视为隐藏历史。PK 缓存转换不会伪造上游缓存证据。
4. 暂停只拒绝该客户在已开启保护组的新请求，不自动换组、不改上游账号状态。现有回答继续结束；排队放行前和 WebSocket 每轮发送前复查。HTTP 返回 `429`、`Retry-After` 和 `group_anti_distillation_paused`；已升级 WebSocket 使用策略关闭码和该错误标识。流式排队若已发出保活，后续只能发送协议内错误，不能改写已经发出的 HTTP 状态。
5. 触发后清空旧窗口；暂停不因新请求续期，期满自动恢复，暂停结束前开始的旧请求不进入恢复后的新窗口。未开启保护的分组、模型列表和用量查询继续按原规则运行。
6. 零缓存是启发式保护信号，正常的独立短请求也可能触发；不能凭它认定客户正在蒸馏，不能解除上游账号的 429 或证明模型降智。建议先在适合长上下文复用的分组开启。

## 集群与兼容

- 配置保存到既有 settings，状态在现有共享 Redis 内按客户归并；Lua 原子完成计数、去重和首次暂停，不新增 SQL 迁移。多应用节点必须使用同一站点的数据库和 Redis。
- 配置在本地短缓存 10 秒；跨节点配置变更最多受此缓存延迟影响。关闭某组不影响其他开启组的共同暂停。Redis 丢失或切换丢失状态后，保护可能重新积累样本，不以统计不可用为由封禁客户。
- 配置加载或 Redis 读取失败时放行，并写脱敏诊断。样本最多 20 条，去重 ID 最多 256 个，配置缓存最多 512 组；闲置状态 24 小时过期。仅保存内部 ID 摘要、零缓存布尔值和时间，不保存请求内容、API Key 或邮箱。
- 邮件复用本站 SMTP。最多 8 个并行任务、每次最多 1 分钟，容量满或发送失败时不阻塞请求、不撤销暂停，也不保证重投。
- HTTP/WS 只增添原始缓存是否已知及媒体证据，不改 token 数值、费用公式、缓存转换/Kilo 开关、首字提前响应、流式时序及原有账务提交。WebSocket 透传的观察延迟至终帧成功写出，既有计费回调与槽位回收顺序保持。
- PK-042 多组 WebSocket 在首帧选组后绑定实际计费组，避免临时握手组误拒/漏拒；本地暂停不计入上游账号健康失败，不触发自动换号或升级到更贵分组。
- 管理接口为 `GET/PUT /api/v1/admin/groups/:id/anti-distillation`。只读权限沿用 `groups.read`，写入仅完整管理员；简易模式仍拒绝分组配置操作。
- HA 运行时补丁、浏览器镜像、外部启动守卫、存储配置和部署工具包保持。本次源码集成不等于现有 HA 节点已部署；未来上线需继续经过当前集群更新流程及兼容校验。
