# HA 后台任务恢复与资源调整

本次依据用户于2026-11-10要求修复渠道统计、五分钟账号糖果测试、账号授权浏览器和双节点卡顿，并明确提高CPU及内存配置。沿用PK-019/034/035/036/047，无新增功能ID。服务器身份、实际连接配置和原始运维回执保存在本机受限记录中，不进入仓库。

本文记录首次故障恢复与候选代次10的范围。用户随后要求检查全部项目、利用数据盘和调整主流量布局，后续角色预算、候选代次11及存储操作见[全项目容量优化记录](PK_CLUSTER_FLEET_CAPACITY_REVIEW.md)，不以本文的历史“worker/数据库保持”描述代替后续实际状态。

## 故障与边界

API请求计费与单活后台worker职责独立。后台worker停止后，原始用量及扣费事务仍持续写入，渠道聚合水位和账号糖果定时任务停止；API手动糖果执行器仍可工作。用户启用的是账号雷达糖果，周期五分钟；分组SVG/糖果配置处于关闭状态，本轮保持。

原管理器的Docker命令统一八秒超时，任何异常都以78退出，而systemd的`RestartPreventExitStatus=78`禁止该状态自动恢复。主机CPU steal持续偏高造成Docker及一秒writer探测延迟，出现一次永久停止和恢复后的误停。副节点CPU空闲，但访问主writer的串行数据库往返增加约40～90毫秒，不能把两节点卡顿都归因于副节点算力不足。

原主API的Docker与Go均限两核；副API虽没有Docker CPU上限，Go并行度仍为二。两者Go软内存上限均为1600MiB。资源调整只针对API，数据库、Redis和worker配置保持；宿主CPU争抢并不会因提高容器配额消失。

授权浏览器缺失消息对应安装前的历史失败记录。两节点现有浏览器镜像及API/worker环境一致，Chromium与Xvfb能在原用户1000和只读根配置下启动；没有通过改写旧失败记录或重新执行历史账号授权隐藏问题。

## 已执行的运行修复

- Docker启动等待改为30秒，其他Docker检查仍八秒；仅`subprocess.TimeoutExpired`使用可重试退出75，身份/配置拒绝及未知异常仍78。原finally有序停止、启动前核对旧worker、两次writer采样及启动后writer复查均保留。
- writer探测预算允许原一秒或经审查的三秒。本次两节点使用三秒；仍验证TLS、节点身份、Patroni scope/member及真实writer角色，非writer响应直接停止，没有忽略失败的宽限期。
- 集群更新代理增加可选`api_resources`，主API为八核/4096MiB、Go3276MiB；副API为八核/8192MiB、Go6553MiB。副宿主实际八核，未配置超出该CPU数的Go并行度。资源进入新候选spec/hash/receipt，后续更新继承配置。
- 复用同一已验证pk.59 HA程序，按原副API、主API、worker顺序完成候选代次10切换；旧请求正常收尾，无强制终止。两API就绪，gate释放，唯一后台worker位于数据库writer，原浏览器运行镜像保留。
- 从原始用量重建中断区间的统计派生表，分十五分钟事务，使用与应用相同的PG advisory lock。再在同一REPEATABLE READ事务内重建相交半天/全天桶并执行二十组对账，全部一致才提交。没有重放计费、修改余额、用量或统计水位；正常聚合已持续刷新。开放粗桶仍遵循原有延迟刷新设计，对账通过只证明该事务快照。

## 源码防复发补丁

`backend/internal/service/channel_monitor_v2_aggregator.go` 增加持久结束水位恢复：每次获得原聚合租约后读data_through，超过十分钟重叠范围时连续追赶。最近事实仍保留的窗口最多一小时；受最短三天事实保留期影响的旧窗口按完整UTC日重建，避免仅用剩余分钟事实覆盖历史汇总。按持久水位所在日推进，跨午夜和进程重启不会反复回退前一天。成功事务推进持久水位，失败保留原段；追平之前不向更早历史回填。保留原五十五秒运行预算、统计口径、租约与保留期，不触碰计费。

`backend/internal/repository/channel_monitor_v2_aggregation.go` 同时修复粗桶删除边界：开始时仅删除目标分钟事实，每一级rollup仅在实际重建时精确删除；完整覆盖一天或半天时必须重建，不能被“同一个桶”的快速跳过逻辑误判。最短事实TTL由两层共享，防止恢复窗口与裁剪规则不一致。

该Go补丁已在现有HA源码上通过隔离定向验证，但本次生产滚动复用了原pk.59二进制，**此Go源码补丁尚未编入生产应用**。当前生产恢复依靠已上线的管理器容错和受审查的一次性派生统计补回；后续正式应用发行仍须按现有发布流程包含该补丁。不得将本次同制品资源切换冒称新Go应用发行。
