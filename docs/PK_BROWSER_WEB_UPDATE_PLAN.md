# 网页更新自动准备浏览器（v0.2.19-pk.11）

基线：私库main及v0.2.19-pk.10，50db3605402073311bc5ef3ee5f2c16e7415cd64。沿用PK-016/017/020/021/036。

## 用户要求与兼容方案

用户要求Jenkins重打包后直接网页更新，旧环境无需手动换镜像、单独安装浏览器或配置路径。pk.10完整部署包已经交付，但仅换二进制不能取得镜像中的浏览器；本版本补齐该路径，旧标签不移动。

旧UpdateService仅解压sub2api且限制下载/解压文件各500MiB，不能依赖旧更新器读取新增tar成员。因此保持原归档布局，将gzip浏览器资源和长度/SHA256尾部直接附加到主程序；附加后同一文件进入镜像、网页更新归档与完整部署包，并统一计入原SHA256。构建限制原归档和主程序各不超过500MiB、资源350MiB、解压总量1536MiB，超限失败而不交付旧更新器无法接收的包。

## 构建与启动

- Jenkins使用可信Dockerfile的runtime-base，单独browser-export stage安装构建期patchelf，给Chrome及其助手预留解释器路径；最终应用镜像仍来自未改写的runtime-base。构建时获取浏览器及库，部署时没有包管理器调用或额外下载。
- 资源包含Chromium、musl加载器、共享库、字体、字体配置、证书及启动入口。构建时解析符号链接，重复库按同一源文件去重；部署端只接受正规文件及指向本次已提取正规文件的内部硬链接，不接受符号链接、外部链接或链接链。避免LLVM/Mesa/ICU别名重复占用更新包与磁盘。只在Jenkins生成资源，不把大型浏览器或真实凭据提交Git。
- 新主程序正常启动时先读取自身资源，校验压缩内容SHA256，在原数据目录browser/.install-*暂存，限制成员路径、数量、类型、权限和解压大小。按最终目录修正预留加载器路径后原子重命名到browser/摘要。正常内核exec让Chrome资源定位正确。
- 首次自动解压、后续同摘要复用；并发实例发布同一资源可接受已完成的目标。不同摘要隔离，保留回退所需目录；中断的暂存目录不作为完成结果。目录写入/空间错误记启动日志，网关继续运行，授权显示不可用，不伪造授权成功。
- 历史镜像默认路径不压过新的内置浏览器；用户其他显式自定义路径仍优先。所有授权代理/凭据/封禁/巡检/cron/账务业务和密钥保持原状。

## 制品验收与发布

browser_profile=pk-browser-in-binary-v1及资源SHA256贯穿inventory/verify/seal/restore/publish和可选旧制品入口；新版本不能移除声明或证据降级。保留旧十一项和pk.10的browser-runtime，增加browser-web-update，共十三项。

新增验收只把原网页归档中的主程序复制到裸Alpine3.21；确认无系统Chromium及其目录，以UID1000、无网络、只读根目录和独立数据卷启动浏览器本地data页检查。运行两次核对首次安装和复用。没有模型请求、真实账号或生产数据；所有临时容器、卷及本机临时目录沿用原清理链。仅用户触发Jenkins时执行，失败不得发布。

## 本轮静态核对

执行源码/数据流阅读、gofmt、Python AST语法解析与git diff --check；未运行本地或服务器构建、测试、真实授权、模型请求，也未连接或更新服务器。没有新增测试文件；扩展既有制品验收入口，实际结果以用户下一次Jenkins构建为准。

交付main及唯一正式标签v0.2.19-pk.11。用户选择ACTION=release、SOURCE_REF=v0.2.19-pk.11，COMMIT_SHA/PACKAGE_ID留空。发布完成后按原网页更新与正常重启流程使用；建议预留至少2GiB空闲磁盘，保留数据和原加密密钥。单进程重启仍有原维护窗口，不宣称热更新。
