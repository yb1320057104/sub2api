# 雷达观测站开发计划

日期：2026-10-30。
基线：私库 `main` / `v0.2.19-pk.4`，提交 `a9bf5e3dc7f791995bbeea91e1e6969d17be5d22`。
状态：pk.7 已交付；当前 pk.8 继续按截图反馈改为标题单行省略、紧凑圆角分页与更淡的失败底色。字号与桌面四列保留；测试、转组与权限逻辑保持。本轮仅静态核对，Jenkins打包和更新继续由用户操作，历史候选证据不代表本轮通过。

## 1. 目标与范围

将现有分组智商测试与账号糖果测试的管理能力集中到管理员专属「雷达观测站」，保留既有测试原理、账号列表操作、历史结果及权限边界。

| 用户需求 | 计划交付 |
|---|---|
| 仪表盘下新增菜单 | 管理员侧栏在仪表盘之后加入「雷达观测站」，同时设置页面路由与服务端权限校验 |
| 分组与账号统一入口 | 页面包含「分组观测」「账号观测」两个页签，配置与运行任务仍各自独立 |
| 分组配置移位 | 复用现有智商测试配置组件和接口；原「智商测试」页面仅展示现有结果 |
| 账号卡片 | 展示名称、平台/类型、用量窗口、当前分组、上次/下次测试、降智判定与合格结果 |
| 多模型糖果测试 | 顶部「糖果测试设置」打开设置弹窗，支持配置多个模型及强度 |
| 不合格自动转组 | 沿用答案21判定与指定目标组，完整答错才转组；请求失败不当作答错 |
| 统一选择控件 | 糖果设置、智商测试、币安自助充值使用项目已有选择组件 |
| 账号筛选 | 全部、合格、不合格；未测试和请求失败不归为不合格 |
| 账号出口 IP | 每模型测试前按账号配置的代理实测；未配置代理才服务器直连，代理失效不兜底直连 |
| 数据隔离 | 新能力通过独立新表承载，不修改旧业务表结构、不搬走或清空历史数据 |

## 2. 保留边界

- 账号列表现有「测试账号连接」、手动糖果测试、结果查看及设置入口保留，多个入口共用同一套设置和任务状态。
- 分组测试继续通过现有分组测试链路执行；账号测试固定使用所选账号、该账号代理及原生连通测试认证/传输链路，不借用分组测试Key。
- 分组与账号的开关、间隔、模型、结果、任务租约独立，打开观测页本身不自动启动测试。任一观测首次开启并保存后，立即唤醒对应调度器执行首轮，不等待一个完整间隔；同时开启时两者分别执行，关闭其中一个不影响另一个。首轮遵守各自已选分组/启用模式、账号可调度状态及目标组排除规则，后续按各自间隔运行。沿用启用状态下保存配置即切换代次并重新安排观测的行为，界面明确提示。
- 账号观测展示现存账号，包括停用账号与已移入目标组的账号；糖果测试首版继续支持现有OpenAI全部真实账号类型。其他平台及模拟测试账号显示「暂不支持」，不能误记不合格，暂不扩大模型调用范围。
- 仅取得完整最终答案后判断是否为21；超时、网络失败、协议不完整、工具请求及取消均单独显示，不凭部分文本转组。
- 不修改计费、余额、用量计算、缓存转换、Kilo规则或充值结算；选择组件替换只改变交互呈现。
- 「不影响原来的表」指不改变旧表结构、不清空或重写历史；已有配置保存、账号分组调整及缓存失效仍执行原功能必要的业务写入，不承诺整个数据库完全只读。

## 3. 页面与交互方案

### 3.1 菜单与权限

管理员导航顺序：仪表盘 → 雷达观测站 → 后续现有菜单。建议路由为 `/admin/radar`，页签使用 `?tab=groups` / `?tab=accounts` 保持刷新与回退位置。

侧栏隐藏、前端管理员路由守卫、服务端管理员认证三层一致；普通用户不能通过直接输入URL或调用API读取账号观测数据。原智商测试公开/登录结果展示维持原权限，不公开账号观测结果。

### 3.2 分组观测

将现有「智商测试」的配置区域放入该页签，保留总开关、SVG/糖果配置、分组选择、模型/强度覆盖、间隔及测试Key管理。原页面保留结果类型切换、分组切换、结果卡片及详情。

移动组件不复制第二份配置；从任一相关入口保存后，状态应同步。公开首页结果展示和历史结果查询不随菜单调整改变。

### 3.3 账号观测

顶部放置「全部 / 合格 / 不合格」筛选、结果数量和「糖果测试设置」按钮，沿用项目分页控件。卡片采用项目现有浅色/深色主题、圆角、边框、间距和徽标；宽屏3列、中屏2列、窄屏1列，具体断点按现有布局实现。长账号名省略或换行并提供完整查看，结果采用文字与颜色共同表达，避免只靠红绿区分。

单张卡片从上到下展示：

1. 账号名称与平台/类型徽标，复用账号列表组件和格式。
2. 用量窗口，复用账号列表已有的显示、加载与错误状态。
3. 当前全部分组标签，过多时折叠并可展开。
4. 上次测试、下次测试；自动测试关闭、目标组已隔离、账号停用或不支持时显示真实原因。
5. 降智判定、合格结果和最近运行状态；逐项显示模型名称、强度和结果。卡片直接列出全部不合格模型名称及其答案，不能只写「账号不合格」或仅显示不合格数量。技术失败另列原因，不与答错混淆。
6. 手动糖果测试及详情入口；执行中防止重复提交，实际转组成功后刷新分组信息。

「是否降智」明确表示本系统糖果题判定，不声称测量了模型整体能力；未测试或请求失败显示「待判定」，不显示「已降智」。

卡片结构示意（仅展示字段位置，非真实账号或测试结果）：

```text
┌────────────────────────────────────┐
│ 账号名称              平台 / 类型   │
│ 用量窗口（原账号列表组件）           │
│ 当前分组：标签 / 标签               │
│ 上次测试：时间     下次测试：时间    │
│ 是否降智：判定     结果：合格状态    │
│ 模型A：合格21     模型B：不合格20   │
│ 不合格模型：模型B（答案20）          │
│               [糖果测试] [详情]    │
└────────────────────────────────────┘
```

用量窗口必须复用 `AccountUsageCell` 的批量读取、可视区域懒加载和缓存机制，不为每张卡额外发起外部请求。只轮询当前页任务状态，沿用每5秒更新、页面隐藏暂停、切页/卸载取消请求的行为；旧请求不得覆盖新筛选、新配置或新一轮结果。

### 3.4 选择框统一

采用项目 `components/common/Select.vue`，保持项目已有搜索、弹层、键盘操作、禁用态、错误态和深色样式。多模型采用「可增删模型行」，每行是支持输入自定义模型ID的模型选择框加一个强度选择框；现有Select为单选组件，不强行改成原生多选。

| `components/admin/account/AccountCandyTestSettings.vue` | 2 | 强度、目标分组；同时增加多模型行 |
| `components/intelligenceTest/IntelligenceTestSettings.vue` | 2 | 默认强度、每组覆盖强度，模板按类型/分组循环渲染 |
| `views/user/BinanceRechargeView.vue` | 3 | 收款账号、订单账号、订单状态 |
| `views/admin/orders/AdminBinanceRechargeView.vue` | 3 | 订单账号、状态、订单有效期 |

以上路径均相对 `frontend/src/`，共14个模板位置。智商结果页已有tab，无需为统一样式将tab改成下拉。币安管理员与普通用户页面都覆盖；每日消费复用页沿用自己的现有控件，不扩大到全站替换。

替换时保留数字ID/有效期、空字符串「继承」和null目标组的含义，适配Select的值事件而非DOM事件；保存前显式验证必填项，加载/保存时直接禁用组件，防止Teleport下拉绕过外层fieldset。币安金额精度、倍率、UID、筛选分页、权限和结算逻辑均保持。

## 4. 多模型与结果规则

### 4.1 设置与执行

设置包含自动开关、测试间隔、不合格账号移入分组、模型列表。建议首版允许1～8个启用模型，每个模型独立选择强度，模型ID去重；数量上限是本方案建议，并非旧功能已有约束。保留自定义模型ID输入及现有强度选项，是否可调用仍以账号实际能力和模型映射为准。

间隔沿用现有1～1440分钟，自动测试开启必须选择有效OpenAI目标组。手动不受自动开关限制；没有目标组时只记录判定、不转组。账号列表与雷达顶部设置按钮打开同一个多模型弹窗，保存到同一份配置。

一次测试是一个账号的一轮批次，全部启用模型并行启动，结果仍按配置顺序展示。每模型使用独立且经过身份核对的账号/母号对象，避免共享可变缓存；短结果事务按账号依次提交，不等待其他模型的网络回复。每个模型均复用 `runAccountCandyProbe`，使用固定账号、账号模型映射、配置代理、OAuth/API Key认证和现有TLS/插件传输。单个模型失败后继续其余模型，除非整轮取消、租约丢失或配置/身份变化。

### 4.2 判定矩阵（用户已确认）

已确认规则：任一模型取得完整最终答案且判定不为21，则整轮不合格；全部启用模型都完整回答21才整轮合格。单个模型请求失败不成为不合格证据，也不抹掉其他模型已经取得的完整不合格答案。用户同时明确要求显示具体不合格模型，不能只展示整轮结论。

| 本轮各模型结果示例 | 汇总结果 | 是否降智（糖果题判定） | 转组 |
|---|---|---|---|
| 所有模型均完整回答21 | 合格 | 否 | 不转组 |
| 一个完整答案非21，其余均21 | 不合格 | 是 | 收到该完整答案后立即尝试转组，成功后不重复转组 |
| 一个完整答案非21，另一个请求失败 | 不合格，另有请求失败 | 是 | 由完整非21证据触发，技术失败本身不触发 |
| 部分回答21，其余请求失败/超时/不完整 | 未完整判定 | 待判定 | 不转组 |
| 全部请求失败，或尚无测试 | 请求失败/未测试 | 待判定 | 不转组 |
| 首个不合格结果提交前取消，或配置/账号身份发生变化 | 已取消/结果已失效 | 待判定 | 不执行转组 |
| 不合格与转组已提交，之后剩余测试取消或失败 | 保留不合格及实际转组记录 | 是 | 不撤销已完成转组，也不重新转组 |

完整回复但无法识别出合格答案，继续沿用现有糖果判定器的不合格规则；未取得完整协议终态、没有最终助手文本、工具请求、HTTP/网络错误不进入答案判定。禁止仅搜索正文中是否出现「21」。每模型保留pk.4的4MiB响应、1MiB行/事件、256KiB最终正文限制。

首个完整非21答案立即持久化不合格并尝试转组，其余模型继续使用各自固定账号连接完成测试。最终收尾、异常过期或取消保留已提交的结果及转组记录；尚未完成的部分答案不能触发转组。测试判定与转组结果分开：不合格但目标不可用、管理员已改组或事务失败，卡片仍显示不合格，并明确显示「未转组及原因」，不能假报成功。已在目标组的账号可以手动复测；回答合格不自动恢复以前分组。

### 4.3 不合格模型展示（用户追加要求）

- **卡片直接可见**：每个模型显示配置时的模型名称、强度、合格/不合格/请求失败/运行中等状态；不合格模型突出显示并汇总为「不合格模型：模型名称（答案）」列表。多个模型答错时逐个列出，不只显示第一个，不要求打开详情才能知道哪个模型不合格。长名称可换行或完整展开，不仅凭颜色表达。
- **答案如实展示**：识别到数字时展示实际答案；完整回复无法识别合格答案时显示「未识别出合格答案」，保留既有不合格判定，不编造数字。请求失败、超时、取消和协议不完整只展示各自状态，不进入「不合格模型」列表。
- **详情可追溯**：详情逐模型展示本轮请求模型、推理强度、可确认的实际映射模型、答案、判定、时间、耗时及最终助手回复。使用本轮快照，即使之后修改模型设置也不改变历史名称和判定；不保存原始推理流或凭据。
- **转组说明对应证据**：详情说明由哪些模型的完整不合格结果触发本次转组，并关联该轮模型结果ID；转组未成功时另列原因，不混同测试结果。
- **界面与筛选一致**：卡片汇总、模型列表、详情和服务端「不合格」筛选取同一批次和配置代次，不能拿上轮某个模型失败拼成本轮结论。

### 4.4 筛选与时间口径

- 「合格/不合格」按当前配置代次下最近一轮已终结的汇总判定筛选，由数据库先过滤和计数、再分页，不仅过滤浏览器当前页。已终结包含失败和取消；不得跳过最新未知结果，回退显示较早的合格判定。
- 「全部」包含未测试、测试中、技术失败、取消、失效和暂不支持。请求失败不能放入「不合格」。新一轮运行时，可保留上一轮有效判定并显著标记「测试中」；新一轮终结后以新结果覆盖摘要。
- 修改模型清单/强度等配置后，旧轮次仍在历史可查，但不冒充新配置的合格结果；筛选摘要标记为待重新判定。
- 「上次测试」显示最近一次真实测试起始时间，详情给出结束时间、耗时和状态；历史来源与模型范围必须可见。
- 「下次测试」来自服务器真实调度状态。原实现收尾后按结束时刻加间隔安排下次，本方案保持；运行中标记「本轮结束后间隔N分钟」，不以临时租约到期时间冒充下次测试时间。
- 自动关闭、停用/不可调度/按规则暂停的过期账号、目标组内账号及不支持平台返回空时间及原因。启用后的配置保存沿用原配置代次失效并重新安排到期行为，UI明确提示保存可能使符合条件的账号立即待测。

## 5. 数据库设计：新增表，不改旧表结构

### 5.1 已核实的旧存储

| 功能 | 当前存储 | 本方案处理 |
|---|---|---|
| 分组测试配置 | `settings`中的`pk_intelligence_test_config`键 | 原接口与存储继续使用，仅移动UI入口 |
| 分组测试Key/调度/结果 | `pk_intelligence_test_keys/state/results`，迁移248～250 | 不复制、不改表、不清历史，继续现有分组任务 |
| 账号单模型配置 | `settings`中的`pk_account_candy_test_config`键 | 初始化新配置时只读，保留旧值供回溯/回退 |
| 账号单模型调度/历史 | `pk_account_candy_state/results`，迁移251 | 新引擎接管后不写；旧结果只读展示，旧到期状态可用于初始化新状态 |
| 账号/分组及充值业务 | `accounts`、`groups`、`account_groups`及现有支付/余额表 | 不增加字段、不搬迁数据；仅保留原功能明确需要的业务更新 |

### 5.2 建议新增五张表

以下为逻辑设计，字段名/迁移序号在正式实施时核对仓库后确定，不提前占用迁移号。主键采用项目现有BIGINT风格，时间使用TIMESTAMPTZ，配置版本与租约令牌用于并发校验。

| 新表 | 主要字段 | 约束与用途 |
|---|---|---|
| `pk_radar_account_config` | `id`、`enabled`、`interval_minutes`、`target_group_id`、`generation`、`initialized_from_legacy`、`updated_at`（初始化在单事务内完成，操作者走已有审计日志） | 一份全局账号观测配置；版本化更新，初始化完成后才调度，防止旧页面覆盖新设置 |
| `pk_radar_account_models` | `id`、`config_id`、`model`、`effort`、`enabled`、`sort_order` | 配置下模型ID唯一；启用模型数量和强度由服务端验证 |
| `pk_radar_account_runs` | `id`、`account_id`、触发来源、配置代次/非敏感模型快照、原分组/目标组快照、`status`、`verdict`、转组状态/原因、起止时间/耗时 | 一行表示账号的一轮；聚合判定与转组结果分开，不使用单模型旧result_id |
| `pk_radar_account_model_results` | `id`、`run_id`、模型顺序/请求模型/强度快照、可确认的实际映射模型、`status`、`passed`、`answer`、最终正文、安全错误分类及脱敏后的结构化上游错误详情、起止时间/耗时 | 每轮每模型唯一，关联批次；只保存最终助手正文，不存原始推理流 |
| `pk_radar_account_state` | `account_id`、`active_run_id`、租约所有者/令牌/到期、最近终结轮次、对应配置代次/判定摘要、`next_run_at` | 每账号一行，负责互斥、列表筛选、下次到期与异常恢复 |

索引：新状态表建立到期/租约索引和判定摘要索引；批次表建立`(account_id, started_at DESC, id DESC)`索引；模型结果表建立`(run_id, sort_order)`与唯一约束。所有索引、CHECK和新表之间的外键只落在新表；账号/目标组采用逻辑ID引用及事务校验，避免为本功能改变旧表外键或删除语义。

`status`表示运行进度（等待/运行/完成/部分技术失败/失败/取消），`verdict`表示合格/不合格/未知，转组状态另列。每模型`passed`在技术失败时为null，不能默认为false。数据库与后端共同限制文本大小和枚举；列表响应只返摘要，最终正文按需加载。

建议按账号保留最近30轮新批次及其模型明细，旧表历史不改。相较旧30条单模型记录，多模型存储会增加；每轮最多8个模型、每模型正文最多256KiB，需在实施时按真实账号规模核算容量。清理只作用于新表，排除活跃轮次和摘要正在引用的记录。账号软删除后停止新任务；删除展示规则与原账号权限一致，不通过级联修改旧账号数据。

### 5.3 初始化与旧数据保护

1. 新增独立SQL迁移，只创建上述新表/新索引；不编辑已发布的248～251文件，不对旧表执行ALTER、DROP、TRUNCATE，不回填旧结果。
2. 新引擎接管时，在旧调度排空之后，幂等地只读旧单模型配置，向新表创建一条等价模型配置；沿用原自动开关、间隔、目标组和强度。旧功能关闭时不擅自开启；旧配置非法时停用并显示原因。
3. 已有账号的旧下次到期时间可只读复制到新状态，避免全部账号因升级立即重复测试。配置、模型、初始状态及初始化完成标记由同一初始化锁/事务保护；规模较大需分批时使用配置代次校验的幂等流程，新调度仅在初始化完成后启用。管理员已保存新代次时，中止旧状态拷贝并按新代次安排，不得用旧`next_run_at`覆盖新配置的「立即待测」状态。
4. 旧任务须先排空；崩溃遗留租约只读判断其真实过期/失效，不UPDATE旧`state/results`。旧running记录可以在读取层标注「旧任务已失效」，不修改历史行、不复制成新成功记录。初始化标记只存在新表，失败可重试且不覆盖已保存的新配置及其调度状态。
5. 历史通过`origin=legacy/radar + id`区分来源，避免两张表自增ID碰撞。旧记录显示「原单模型历史」，不凭一条旧结果推断新多模型配置全部通过；原始时间、答案和转组记录不变。
6. 原分组配置保存/专用Key同步仍可正常写入`settings`、`api_keys`和分组专用表；明确不合格转组仍需更新`account_groups`及`scheduler_outbox`。这些是原功能业务操作，不是迁移改写旧数据；充值选择框更换不新增任何支付表写入。

## 6. 任务调度、转组与切换

### 6.1 一个账号只有一个执行入口

雷达手动、原账号列表手动与定时任务都调用同一新账号引擎；每账号仅一个活跃批次，重复点击返回现有任务或明确运行中。分组测试仍保留独立调度器。

跨账号每实例最多8个任务，每账号最多8个模型同时请求，即每实例最多64个模型调用。每模型仍最多5分钟，整轮预算6分钟。账号租约6分钟窗口、每30秒续约，必须同时匹配所有者/令牌/active_run_id；丢失租约立即取消剩余请求，旧持有者不能再次写终态或转组。已经提交的不合格/转组证据在过期恢复中保留。

保存配置增加代次并取消旧批次；手动和自动共享互斥。进程异常后的过期任务恢复独立于自动开关，不能让失败手动任务永久占用；后台启动门、停止等待和上下文取消继续复用PK-019。

### 6.2 转组事务

整轮收尾时重新核对配置版本、租约令牌、账号/母号认证和连接快照、当前分组是否被管理员改变、目标是否存在/启用且符合准入条件。快照中的敏感身份摘要只用于内存比较，不写结果或日志。

首个符合条件的完整不合格模型，在同一事务中完成：保存该模型结果 → 删除该账号原有全部分组关系 → 仅加入选定目标组 → 更新批次/调度摘要 → 写入既有缓存失效outbox。一个批次最多成功转组一次，提交失败整笔回滚；缓存异步生效沿用既有机制，不宣称所有实例瞬时同步。

### 6.3 新旧调度切换与回退

新租约在新表，旧二进制无法识别；仅复用事务级advisory lock不足以防止事务外模型调用重叠。部署必须通过既有后台activation机制先停止旧账号调度、排空或取消旧任务，并确保旧实例不再接收账号手测，再启动新所有者。不得在多实例滚动期间同时让新旧账号引擎工作；正常网关流量按既有部署策略交接。

回退先停新任务并排空，再恢复兼容的旧服务。新表保留，旧版看不到新多模型历史；旧版恢复的是保留下来的旧单模型设置，不能声称自动继承新配置。恢复自动测试前核对其旧开关/目标/间隔，已经完成的合法转组不会因程序回退自动撤销。本轮部署为新建独立服务，不执行原生产服务切换或停服。
