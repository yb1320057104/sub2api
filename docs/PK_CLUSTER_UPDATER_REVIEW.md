# 集群应用统一更新器

此前单节点更新路径不能统一维护两台API和各自的后台worker，也不能把正式应用版本与集群HA构建后缀分开显示。本次增加 `deploy/cluster-updater/`：管理员确认一次私库正式Release，更新器从确定提交构建一份保留HA能力的程序，按顺序更新现有两节点，并单独显示API与worker实际版本。

本次扩展PK-047，沿用PK-016、PK-017、PK-021。交付运维工具源码及说明，不修改普通应用版本文件，不创建新应用标签，不改动或覆盖已发布应用制品。新机安装仍使用 `deploy/cluster-kit/`；本更新器只适配已部署、已接受的HA r4两节点运行协议。

## 更新和恢复合同

1. 只把私库已公开的正式Release作为候选，排除草稿、预发布及仅main上的提交；核对标签剥离后的提交属于main历史。管理员确认绑定候选标签、提交及两节点观测版本，候选或现状变化后需要重新确认。
2. 从确定提交导出源码，校验并合并HA补丁；不读取开发工作区未提交改动。构建容器不获得生产凭据、生产数据、SSH密钥或Docker管理接口。补丁冲突、源码身份变化或数据库迁移文件路径／内容哈希映射与已验证基线不同，均拒绝自动部署。
3. 两节点均通过只读更新预检后，上传同一SHA256程序并准备停止状态的API和worker候选。保留原环境、网络、数据和TLS挂载；页面、插件等可变数据继续使用原路径，不用提前复制的快照覆盖后续修改。
4. 顺序固定为副API、主API，然后两节点worker。更新每台API前从两入口摘除目标并确认对端就绪；取得同一gate代次的持有权后，等待旧HTTP请求和计费工作收尾，正常终止旧进程，验证新程序及真实存储就绪，再更新接受包、释放gate并恢复入口。不会强杀仍在处理的模型流，也不跨节点重放已发送模型请求。
5. 每台worker由现有监督器控制。停止监督器并等旧worker正常退出后，更新其程序身份、规格与版本，恢复监督器并验证其跟随本机PostgreSQL writer。最终要求两API与两worker版本一致、两API就绪、恰有一名活动worker且位于当前writer。纯仲裁节点不运行应用程序，不参与应用版本更新。
6. 每步记录私有操作状态并拒绝重放。更新失败立即停止后续节点；仅当持有权、旧规格、接受包及健康证据均可验证时恢复当前节点。入口动作回应丢失时，协调器也会检查已尝试的入口，避免已摘流的健康目标因缺失回应一直留在排空状态。恢复证据不完整则保留失败状态供检查，不推测接管或继续。

程序回滚不撤销数据库迁移。更新器不升级数据库、Redis、etcd或操作系统，也不改变存储复制与选主策略。stage中途失败可能保留停止候选；处理重放拒绝或候选占用时，需要先核对操作归属，不能删除来源不明的容器或覆盖原数据。

## 源码与权限边界

| 文件 | 职责 |
| --- | --- |
| `server.py`、`app.js`、`index.html` | 管理员鉴权、候选确认、任务状态和节点版本展示。 |
| `builder.py`、`prepare_overlay.py` | 私库正式来源、固定源码与HA补丁校验、隔离构建及迁移映射门禁。 |
| `cluster_rollout.py` | 两节点预检、制品分发、双入口切流、串行更新和最终角色核对。 |
| `agent.py` | root私有配置下的限定节点RPC，校验并复用已有gate、候选、入口及worker监督协议。 |
| `README.zh-CN.md` | 适用条件、流程和私有配置字段说明。 |

远端访问使用固定主机密钥和SSH forced command，仅接受限定JSON请求及受大小／哈希校验的程序上传；该密钥不提供交互shell、转发或SFTP。代码中不附带现有站点地址、域名、SSH身份、密钥、令牌、真实配置、容器数据或历史回执。HA补丁由仓库已有cluster-kit清单与固定源码生成，不重复装入大体积生成目录。

本机健康接口schema2、页面、脚本返回200；未登录状态读取401，无效管理员令牌403，错误Origin提交403。公网页面与脚本返回200且逐字节SHA与安装源码相同，未登录状态读取401，两域名/ready均200。首次Python urllib公网探测遇到403，未计为成功；随后使用curl完成上述状态与内容核对。没有以编造或重放管理员登录令牌做验收，管理员成功鉴权与确认状态机由本地模拟覆盖。

首次只读版本检查发现已审计源码基线含正式pk.58发布后的纯文档提交，严格祖先检查因此误拒绝当前正式标签；已仅为固定、已核验应用源码等价的pk.58正式提交添加准确匹配并补测试，后续真实检查恢复in_sync。未来正式版本仍须属于私库main历史且满足HA来源与迁移门禁。

## HA运行版本后缀比较修复

应用后台此前把运行版本的`pk.58-ha.20261108.4`整体交给无符号整数解析，失败后将PK修订视为0，因而把同基线正式pk.58误报为更新。新鲜GitHub结果与缓存结果使用同一比较函数，所以清除缓存不能解决此问题。

补充补丁仅在版本比较入口剥离严格匹配的HA／secondary日期与构建号后缀。实际current_version、build_type、正式标签准入以及非release构建的原地更新／回退拒绝保持；已有前端根据has_update=false显示“已是最新”。同基线的日期与构建号变化不构成正式版本更新，未来pk.59或更高上游版本仍正常提示。未知及畸形后缀保留原语义。

补丁及两份受影响的既有源码／测试文件哈希位于`deploy/cluster-updater/patches/`。生成器先完整验证固定r4准备源码，再在独立临时git目录应用补丁并验证结果，生成96份合并输入和6组定向测试清单。它不读取未提交工作区，也不修改原cluster-kit r4包、数据库迁移、普通应用入口或已发布正式标签。原94文件基线的历史核验记录仍只描述上一轮。
