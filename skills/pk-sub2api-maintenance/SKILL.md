先按 [清单定位与登记说明](references/protected-features.md) 读取工作区当前 `PK_FEATURES.md`；不要另维护一份过期功能列表。

2. `origin/main` 是自己的正式分支。先获取私库状态，再 fetch 作者指定的 tag/分支，记录实际 commit。未指定版本时查询作者当前正式发布，选定后固定 commit；不要把 `latest` 当作永久不变的来源。

5. 按仓库 PR模板记录作者来源 commit、逐项二开核对、清单更新与冲突处理；静态核对完成后直接提交、推送，不自动运行完整源码测试或绑定 notes。若实际运行了可选测试，记录真实环境及通过、失败、部分执行或取消结果，静态、历史与本次动态证据分开；没有运行就明确写未运行。直接提交也提供同样说明，不能伪造验收结论。

## 发布、更新或恢复

涉及发布/部署/回退时读 [私有发布与恢复](references/private-release.md)，并核对私库当前 `Jenkinsfile`、`deploy/jenkins/README.md` 和 `PK_MAINTENANCE.md`。Jenkins 可信 SCM 固定读取已审阅的私库 `main`，先核对实际任务配置与仓库初始化一致；工作区缺少这些入口不构成重新使用 GitHub Actions 的理由。

默认正式流程为 **二开保留与静态核对 → 直接提交、推送并合入 main → 推送正式标签 → 用户手动 Jenkins `release` → 按授权网页更新**：

1. **提交与标签**：完成当前变更的静态核对、二开登记及私库 `main` 推送。确认正式标签、Release 和已有发布状态未占用，创建并推送 `vX.Y.Z-pk.N`，核对远端标签剥离后的 commit。不得移动或覆盖已推送正式标签；不要求源码测试报告或 notes。
2. **用户手动 release**：Jenkins `sub2api-package` 使用 `ACTION=release`，`SOURCE_REF` 默认留空，由用户从分支/标签列表选不带 `origin/` 的正式 `vX.Y.Z-pk.N` 标签，`COMMIT_SHA` 和 `PACKAGE_ID` 留空。标签提交必须在私库 main 历史内；分支/裸 SHA 或 COMMIT_SHA 覆盖均拒绝，SOURCE_REF 不改变可信流水线 SCM。
3. **构建与发布**：新 Jenkins 使用 `pk-artifact-only-v1` 封存配置，不获取或读取源码 notes，执行 build → inventory → 专用 daemon 的 `pk-artifact-v2` 十一项运行时验收 → seal → publish。同一二进制进入镜像和更新归档，制品验收通过后发布原包，不重新编译；运行时不连接生产、不接收发布凭据。记录 package_id、运行时证据与制品 SHA256。取消源码门禁不取消私有来源、版本归属、制品运行时验收或封存完整性校验。
4. **网页更新**：正式非 prerelease Release 的归档与 `checksums.txt` 发布成功后，原网页更新入口可发现该版本。执行更新仍遵守当前用户授权；release/publish 不自动升级或重启生产。

用户只要求试打包时显式使用 `package`，不能因缺少源码 notes 把正式交接降为候选打包。旧 `pk-source-artifact-v2` 封存包继续核对 source 与 runtime 两套证据，旧手动 `pk-local-v1` 路径按其原有格式兼容；`publish` 也可处理已验收封存但尚未对外发布的新流程包。旧包已封存的源码报告、运行时报告和哈希必须保持完整，不删除或重写旧证据绕过校验。历史 notes 可保留为历史证据，不是新 release 的必需输入。已推镜像或留下草稿的部分失败先核查版本阻挡，不承诺自动恢复或覆盖重发。可选测试的服务器入口、受限凭据、工具镜像与隔离/清理边界见引用文档；入口和配置完成不等于实际通过。

交付时说明：私库分支/提交、上游版本、PK版本或已推送正式标签、受影响/新增 PK ID、清单与静态保留依据、可选测试是否执行及其真实结果、Jenkins 制品结果或待用户点击的准确参数，以及本次是否进行了线上操作。没有读取线上状态时，写“本次未进行线上变更；线上实际版本未核实”，不推断其他人是否更改了线上。
