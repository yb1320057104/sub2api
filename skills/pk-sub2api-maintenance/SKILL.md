# PK版 Sub2API 维护

## 固定来源与用户要求

- 正式源码、源码恢复、发布包和回退版本：`https://github.com/pengkang0322/sub2api`，必须为私有仓库。
- 镜像：`ghcr.io/pengkang0322/sub2api`，必须为私有镜像。
- 原作者 `https://github.com/Wei-Shaw/sub2api` 仅作为 `upstream` 的合并输入。不要直接安装、部署或恢复它的程序和镜像；私库不可用时说明原因并保留当前服务。
- 页面显示“版本号 + PK出版”，保留网页顶部的一键更新和版本回退，全部从私库获取。
- 缓存转换、费用转换、下游 usage 改写及其他已有功能必须保留。不能用官方目录覆盖二开，也不能因为自动合并无冲突就认定业务安全。
- 工作区根目录 `PROJECT_CONSTRAINTS.md` 是项目约束，`PK_FEATURES.md` 是唯一二开功能登记表；优先读取当前私库工作区版本。每次合并上游逐个核对所有有效 PK ID，功能不得被覆盖或改变；新增/扩展二开必须在同一变更中登记，发现遗漏也必须补齐。受影响项待验证或清单未同步时不能合入/发布。用户明确要求改变对应功能时保留原 ID 和变更依据。
- 2026-10-03 用户明确改为 Jenkins 打包、本地电脑测试，不再使用 GitHub Actions 打包或测试。候选及正式发行构建只在 Jenkins 进行；本机允许测试所需编译和自动清理的测试夹具，不运行发行构建。使用工作区 `scripts/test-local.ps1`（WSL）或 `scripts/test-local.py`（Linux），缺依赖或失败不得冒称通过。新生成的临时测试文件用完删除，保留原有回归文件。
- Jenkins 只绑定本机 `127.0.0.1:18081`，不开放公网入口；用户自行配置域名反向代理。迁移打包位置必须保留原网页一键更新、回退和私库 SHA256 校验链。
- 完成本次请求范围内的代码和核对。只请求恢复源码或合并时，不默认扩展为正式发布或上线。线上更新、重启、数据恢复以用户的明确授权为准；已经授权当前操作时不要重复请求。此 skill 本身不扩大操作范围。
- 不把密码、token、数据库配置或服务密钥写入 skill、源码、提交或普通日志。
- 线上部署和恢复默认保留正在进行的请求：先验证候选，再平滑切换代理，旧实例留到真实连接和计费队列排空。网页单进程更新会重启，不能把它称为热更新；只有用户接受维护窗口时才使用会中断请求的方式。

## 开始时识别上下文

1. 找到当前工作区，读取其 `AGENTS.md`、`PROJECT_CONSTRAINTS.md`、`PK_FEATURES.md` 和相关的 `PK_MAINTENANCE.md`。已知初始路径是 `C:/Users/93065/Downloads/sub2api-main`；不要假定路径永久不变。根目录 `AGENTS.md` 和约束/清单必须随私库提交与恢复。安装目录中的 skill 不能代替最新工作区清单；找不到时先从可信私库获取，不能视为没有二开。
2. 检查 `git status`、`origin`、`upstream` 和当前分支；任务涉及线上部署准备时再核查线上实际版本。`origin` 应为用户私库；`upstream` 是作者仓库。不得改动无关仓库。
3. 本地目录丢失或没有 Git 历史时，从 **用户私库** 恢复到新目录，再对照现有文件；保存尚未提交的本地改动，不能覆盖它们。私库首次基线标签为 `pk-baseline-20260930`，当时上游基线为 `a60a29549f488a854966aaec9541abbe006cac22`。
4. 核对私库访问和发布权限。Jenkins 源码读取使用本私库只读 deploy key，正式发布使用独立的 Release/包写入凭据；网页读取 Release 需要该仓库 Contents:read，私有 GHCR 拉取需单独的包读取凭据。不要把开发者的宽权限 token 直接复制到 Jenkins 或生产；缺少发布凭据时可以准备/验证打包，但不得称为已发布。

私库不可访问时，可使用用户指定或已有记录证明来源的本地私库克隆/备份，核实提交后恢复。没有可信源码就停在访问问题和恢复方案；不根据功能清单重写代码冒称完整恢复，也不保证找回从未提交、没有备份的改动。

## 合并原作者更新

先按 [清单定位与登记说明](references/protected-features.md) 读取工作区当前 `PK_FEATURES.md`；不要另维护一份过期功能列表。

1. 保留当前可恢复的提交/标签及二开差异；若工作区有其他进行中的工作，使用可用的隔离 checkout，不能靠覆盖或强制 reset 清理。
2. `origin/main` 是自己的正式分支。先获取私库状态，再 fetch 作者指定的 tag/分支，记录实际 commit。未指定版本时查询作者当前正式发布，选定后固定 commit；不要把 `latest` 当作永久不变的来源。
3. 在 `sync/upstream-版本或分支` 上合并作者提交，保留父提交关系。合并前后按每个有效 PK ID 记录“已保留 / 无影响 / 待验证”及依据，审查所有新调用路径；保留作者修复与自己的扩展，不能机械地全部选 ours/theirs。清单路径不是白名单，未登记的既有二开也要补齐并保护。
4. 尤其审查计费拆分、余额预留、长上下文定价、新模型定价、协议入口/出口和账号 extra 保存。文本无冲突仅代表能合并，不能替代业务核对。
5. 按仓库 PR模板记录作者来源 commit、逐项二开核对、清单更新、冲突处理、本地测试报告与 Jenkins 构建结果。授权直接提交时也提供相同说明。区分静态核对、历史云端证据和本次本地结果，检查完整 commit/tree、真实执行清单与跳过项；缺依赖或未运行的测试不得写成通过。
6. 按当前请求范围交付私库分支/PR，或合入自己的 `main`；只有用户同时要求发布时才创建正式标签和 Release。候选检查产物与正式 Release 要区分，后者会进入网页更新列表。

不要使用 `git push --mirror`、`reset --hard upstream/main`、强制推送或整目录覆盖来同步。不要把上游所有标签一次性推到私库；只推本次需要的自有标签。

## 发布、更新或恢复

涉及发布/部署/回退时读 [私有发布与恢复](references/private-release.md)，并以仓库最新 `PK_MAINTENANCE.md`、`Jenkinsfile` 和 `deploy/jenkins/README.md` 为准。Jenkins 先打包，本机对同一提交和制品完成十套件验收后再发布；发布必须复用已验证制品，不重新编译。

交付时说明：私库分支/提交、上游版本、PK版本（如已发布）、受影响/新增 PK ID、清单同步与保留功能的证据、本地测试报告及 Jenkins 制品结果，以及本次是否进行了线上操作。没有读取线上状态时，写“本次未进行线上变更；线上实际版本未核实”，不推断其他人是否更改了线上。
