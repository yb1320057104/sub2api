# 私库发布、网页更新与恢复

## 来源

- 源码和 Release：`pengkang0322/sub2api`，私有。
- 镜像：`ghcr.io/pengkang0322/sub2api`，私有。
- `Wei-Shaw/sub2api` 只作为合并源，不能作为部署、安装、回退或恢复失败时的兜底。
- Go module/import 中保留原作者路径是正常的代码标识，不要全局替换这些字符串。

## 发布

仅在当前请求包含发布时执行本节。读取私库当前 `.github/workflows/release.yml`；推送、PR、标签、正式发布和后续工作流的触发链均应核实，确认不会引发未授权的生产部署。最初流程为手动 **PK Release**，输入已经推送、审阅过的标签，例如 `v0.2.10-pk.2`。不要把例子当成当前最新版。

版本为 `上游版本-pk.修订号`；相同上游版本继续递增修订号，不复用已使用的标签。页面在机器版本后追加 `PK出版`，不能把中文写入机器版本。

同一构建产出的二进制必须同时进入镜像与更新归档，Release 必须带对应平台的 `sub2api_版本_linux_amd64.tar.gz` 和 `checksums.txt`。只有镜像不能支持网页一键更新。PK Release 为正式发布，不能被 GitHub 标为 prerelease 后又期望 `/releases/latest` 找到它。

在 GitHub 云端检查前端、Go 更新模块和持久化启动；等待结果，失败就修复对应问题，未通过的版本不能称为可上线。最初的发布工作流不自动更新生产；以后必须查看当时实际工作流，不能沿用这个历史结论。仅供核对的候选使用 CI 制品或草稿，不把正式 latest Release 当成不会影响更新列表的候选。

确认源码仓库和 GHCR 包各自的 private 状态；两者可见性独立。镜像版本必须匹配服务器架构。初始服务器为 x86_64，最初仅发布 linux/amd64；不要推断 Apple/arm64 已支持。

## 凭据

- 网页 Release 下载：运行环境的 `UPDATE_GITHUB_TOKEN`，优先只针对该私库的 Contents:read fine-grained token。
- 宿主机拉镜像：单独登录 GHCR，使用具备 read:packages 的适用凭据；不要把网页 token 当成已登录 Docker。
- Actions 自身用 GITHUB_TOKEN 发布；创建工作流需要相应 GitHub 授权。
- 将凭据放到受保护的服务器环境或秘密存储，不进仓库、不进 skill、不打印值。缺少授权时明确所需权限，继续能独立完成的工作。

## 网页一键更新与重启

PK 容器启用 `SUB2API_DOCKER_SELF_UPDATE=true`，运行应用用户可写的 `/app/data/bin/sub2api`，使用已有 `/app/data` 持久化卷及 restart policy。

- 同镜像重启/重建保留网页更新版本。
- 不同镜像种子哈希触发原子安装该镜像程序。
- 私有API资产下载需要授权，转向GitHub CDN后去掉Authorization，所有归档核对SHA256。
- 版本比较必须识别 pk.1、pk.2、pk.10 的数值顺序。
- 运行库、资源目录、entrypoint 等镜像变更需要对应镜像部署，不能仅靠网页替换二进制。

## 回退和恢复

1. 先确认用户要恢复的是源码、应用版本还是业务数据；不把源码恢复扩展成清库。
2. 源码从私库的分支/commit/tag 恢复。保留当地尚未提交的改动；目录丢失时从私库重新 clone。
3. 在线可用时，网页回退读取用户私库的旧正式 Release。旧官方版本不能充当候选。
4. 手动镜像回退需保留已有 Compose 的所有 `-f`、`--env-file`、project 名称和数据卷，只操作应用服务。
5. 同一旧镜像曾经过网页升级时，直接 pull/recreate 会保留升级程序。按私库当前指引先停应用，使用该服务的临时维护容器仅清除 `/app/data/bin/.image-seed.sha256`，再强制重建应用。不要删除 `/app/data`、卷或数据库。
6. 回退前核对数据库迁移兼容性并备份；业务数据恢复只能使用用户明确选定的备份，不能假定退镜像能撤销数据库迁移。

执行线上操作前检查已有明确授权。用户明确说“线上先别动”时，交付本次成果并等待其后续指示，不主动催促上线。用户已提出部署但尚未批准具体切换时，先完成可审阅准备，再以目标PK版本、涉及服务、备份和回退方式请求最后确认；不反复询问已批准的同一操作。
