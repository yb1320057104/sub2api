## 发布

仅在当前请求包含发布时执行本节。读取私库当前 `Jenkinsfile`、`deploy/jenkins/README.md` 和 `PK_MAINTENANCE.md`；核实推送、PR、标签、打包与正式发布的触发链，确认不会引发未授权的生产部署。自 2026-10-03 按用户要求由 Jenkins 打包，后续本地电脑测试按当次明确授权执行，GitHub Actions 不再执行这两项工作。本次 Jenkins 迁移不运行任何本地构建或测试；未来流程不覆盖当次禁令，也不降低发布验收门禁。Jenkins 仅在 `127.0.0.1:18081` 监听，用户自行配置域名反代；不要开放公网端口。

版本为 `上游版本-pk.修订号`；当前版本完成既定合入/发行后，规划同一上游版本的下一次发行时才核对标签并递增修订号；未发布版本内的修复和重新打包不递增，不复用已使用的标签。页面在机器版本后追加 `PK出版`，不能把中文写入机器版本。

新的工作分支以目标未发布版本命名为 `codex/vX.Y.Z-pk.N`，例如 `codex/v0.2.13-pk.1` 只是格式示例。同一目标版本的功能、修复、文档和上游合并复用一个分支及一个 PR，不为反复修复/打包递增版本或添加任务、日期、助手、功能后缀。新建前核对本地/私库远端分支、在途 PR 和私库标签；目标版本未明确时先明确，不先建临时分支。默认只有一个在途版本，确需并行不同版本须用户明确要求；新版本分支从已核对的私库 `main` 创建，`main` 的原审核、测试和发布门禁不变。

本次不删除或改名已有分支。当前 Jenkins 仍使用固定的 `codex/jenkins-build` 完成既有迁移，收尾后按既定流程切到已审阅的 `main`，不能因新命名规则中断此引用。未来分支清理必须先确认已完成该变更既定的合入/发行流程、没有未保全的独有提交、无在途 PR/Jenkins/worktree 引用，再按授权执行，不强制删除。

同一构建产出的二进制必须同时进入镜像与更新归档，Release 必须带对应平台的 `sub2api_版本_linux_amd64.tar.gz` 和 `checksums.txt`。只有镜像不能支持网页一键更新。PK Release 为正式发布，不能被 GitHub 标为 prerelease 后又期望 `/releases/latest` 找到它。

Jenkins 选择 `ACTION=package`，在 `SOURCE_REF` 的可搜索下拉列表选择已审阅的新标签 `vX.Y.Z-pk.N`，生成待验收包。该列表使用 Git Parameter `PT_BRANCH_TAG`，默认 `origin/main`；选择目标版本已有的 `origin/codex/vX.Y.Z-pk.N` 分支生成候选包，本次迁移仍可使用原有 `origin/codex/jenkins-build`。日常将 `COMMIT_SHA` 留空，仅需固定提交时填写 40 位小写 SHA，覆盖下拉选择并生成候选。流水线将分支/标签规范化为完整 ref 后继续执行原有校验，正式标签仍须位于私库 `main` 历史；选择源码不改变可信流水线的 SCM 分支。

后续获准执行本地验收时，下载该包并在本机以 `scripts/test-local.ps1 -ArtifactDirectory ...` 或 `python3 scripts/test-local.py --artifact-dir ...` 执行源码与镜像持久化完整验收。缺 WSL/Docker/工具或套件失败时明确报告，不把打包成功写成测试通过。

本地报告必须绑定相同 commit/tree、package_id、二进制和镜像归档 SHA256，十个套件全部通过；按 `{package_id}.json` 上传到 `/srv/jenkins-evidence/sub2api/`。Jenkins `ACTION=publish`、`PACKAGE_ID=...` 校验报告后复用原制品发布，不重新构建。只有源码测试、未跑 artifact-runtime 或缺发布凭据时不可正式发布。候选包不进入正式 latest 更新列表；发布不自动更新生产。

原网页一键更新能力必须保留：正式 Release 继续是私有仓库中的非 prerelease，带既有名称的二进制归档与 `checksums.txt`；前后端更新 API、凭据来源、回退和 SHA256 校验行为不因迁移 Jenkins 改变。历史云端验收报告保留原记录，不改写为本次本地验证。

确认源码仓库和 GHCR 包各自的 private 状态；两者可见性独立。镜像版本必须匹配服务器架构。初始服务器为 x86_64，最初仅发布 linux/amd64；不要推断 Apple/arm64 已支持。

## 凭据

- 网页 Release 下载：运行环境的 `UPDATE_GITHUB_TOKEN`，优先只针对该私库的 Contents:read fine-grained token。
- 宿主机拉镜像：单独登录 GHCR，使用具备 read:packages 的适用凭据；不要把网页 token 当成已登录 Docker。
- Jenkins 读取源码使用只读 deploy key；正式发布使用独立的私库 Release 写入和 GHCR 包写入凭据，缺少时阻止发布，不复制开发者宽权限 token。
- 将凭据放到受保护的服务器环境或秘密存储，不进仓库、不进 skill、不打印值。缺少授权时明确所需权限，继续能独立完成的工作。

## 网页一键更新与重启

PK 容器启用 `SUB2API_DOCKER_SELF_UPDATE=true`，运行应用用户可写的 `/app/data/bin/sub2api`，使用已有 `/app/data` 持久化卷及 restart policy。

- 同镜像重启/重建保留网页更新版本。
- 不同镜像种子哈希触发原子安装该镜像程序。
- 私有API资产下载需要授权，转向GitHub CDN后去掉Authorization，所有归档核对SHA256。
- 版本比较必须识别 pk.1、pk.2、pk.10 的数值顺序。
- 运行库、资源目录、entrypoint 等镜像变更需要对应镜像部署，不能仅靠网页替换二进制。

网页更新/回退有单进程重启窗口，当前重启入口直接退出进程，不会完成流式请求、WebSocket 和异步计费排空。不要用网页重启执行要求保留在途请求的切换；下面的人工蓝绿流程与网页更新是不同的运维方式。

## 需保留在途请求时：人工蓝绿热切

开始前读仓库最新 `PK_MAINTENANCE.md` 的完整流程及当前开关实现。此处不授予新的线上权限。2026-09-30 最终按用户明确允许硬切断流的授权完成；后续部署以当时授权为准，不反复询问已批准的同一操作，也不把历史授权当作永久自动部署许可。

1. 固定私库已验证的 PK 标签和镜像 digest，记录旧实际程序版本、镜像、代理及 Compose 参数，备份数据和配置。确认新旧程序可同时使用生产 DB/Redis，包括启动迁移、Redis 键和请求状态。0.2.11 已引入默认开启的余额并发预留；旧实例不会登记新机制的预留，混合版本不能假定覆盖全部在途请求，须按当前维护文档验证兼容性。
2. 新容器使用独立名称、旁路本机端口和**独立 `/app/data` 副本**，保留权限、配置和资源。核对在线复制期间变化的文件及后续同步方案，不与旧实例共享可写程序/定价/激活标记。DB、Redis DB、JWT 和加密密钥保持一致；另建 Redis 会分离并发和认证状态，不能用它绕过兼容问题。
3. 只在已实现并经过隔离远端验证的 PK 二进制上设置以下环境变量。新数据副本里的激活文件必须不存在；若复制带入旧标记，只清除新副本中的标记。核对副本中持久化程序版本，必要时仅重置新副本的 `.image-seed.sha256`，由所选私库镜像安装程序，不碰旧卷。

   ```dotenv
   SUB2API_SKIP_STARTUP_SLOT_CLEANUP=true
   SUB2API_BACKGROUND_ACTIVATION_FILE=/app/data/.background-active
   ```

   第一个开关防止新进程清除旧实例的在途并发槽位/等待计数；第二个让受控后台任务等待启动标记，避免定时测试和主动探测重复执行。它不是所有后台工作的总暂停开关：请求记账、缓存失效及已有锁保护的必要服务仍会工作，初始化/迁移仍须检查。仅向不支持这些开关的旧镜像加环境变量无效。
4. 保留旧实例及其后台。启动新实例后核对版本、跳过清理和等待激活日志。免费验收使用 `/health`、首页/资源、`GET /api/v1/settings/public`、现有登录态的用户资料和账号配置；公开设置真读数据库，`/health` 只返回常量。另从新实例网络、用其实际凭据验证 DB `SELECT 1` 和 Redis `PING`。没有通用 `/ready`；共享 Ops 历史健康可能来自旧实例。不要点击账户测试、主动探测、网页更新或重启，也不要发模型生成请求冒充免费检查。
5. 检查 OpenResty 完整有效配置及旧 worker 继承的配置，确认没有 `worker_shutdown_timeout` 或其他强制结束旧 worker 的倒计时。不能只删除新配置中的超时就假定旧 worker 不受限。配置检查通过后 graceful reload，将新流量切到新实例；保留旧 worker、旧容器和 SSE/WS 配置。不重启代理，不对已发送的计费 POST 启用 `proxy_next_upstream non_idempotent` 重放。
6. 观察新连接是否命中新实例，同时确认旧实际 HTTP/流式/WS 自然结束、旧 worker 不再接流量、异步 usage 和额度/余额写入完成。共享并发数为 0 不能证明本机排空：WS 每轮结束释放槽位，但连接仍可发下一轮。部分 WS 续链状态在本机，新连接跨实例续链须独立验收，不能声称迁移现有连接。当前没有完整实例级排空 API，固定等待时长不能代替证据。
7. 仅在排空确定后才让旧容器退出，并为后台清理留足时间，确认旧进程正常退出。旧程序 HTTP Shutdown 只等 5 秒；默认 `docker stop` 宽限期可能强杀，不能把它当作排空机制。确认旧后台已停，再在新实例自己的数据目录里创建临时普通文件，同目录原子 rename 到 `/app/data/.background-active`，无需重启新进程。验证后台仅启动一次。该标记是一次性启动门，激活后删除文件不会暂停任务。
8. 记录版本/digest、备份、代理切换及连接排空/后台交接证据，保留旧容器和数据以便回退。任何条件未知时，保留旧实例、旧后台和当前可用流量路径；新后台继续等待，不强停连接以追求完成。

## 回退和恢复

1. 先确认用户要恢复的是源码、应用版本还是业务数据；不把源码恢复扩展成清库。
2. 源码从私库的分支/commit/tag 恢复。保留当地尚未提交的改动；目录丢失时从私库重新 clone。
3. 先核对数据库迁移兼容性并备份；业务数据恢复只能使用用户明确选定的备份，不能假定退镜像能撤销数据库迁移。私库不可用时保留当前服务，不回退到原作者发行物。
4. 无维护窗口时先热回滚：旧实例仍在且就绪时，通过代理 reload 将新连接切回旧实例，同时保留新实例已有请求；旧实例已停时，按上面的蓝绿流程准备受支持的私库旧版本、独立数据副本和共享依赖，验证后再切流。持有现有连接的实例继续运行，后台仍由当前活动实例承担，直到其排空并退出后再激活接替实例。不要把不识别蓝绿开关的旧版本直接连到共享生产依赖。
5. 网页回退仅读取用户私库旧正式 Release，并会产生重启窗口；只能在用户允许中断的维护安排下使用，不能代替热回滚。旧官方版本不能充当候选。
6. 手动停机镜像回退也仅允许在已获准的维护窗口内执行。需要保留请求时先证明排空；若用户明确允许断流，可不等连接自然归零，正常停止应用并尽力完成记账清理，记录无法证明的排空边界。保留已有 Compose 的全部 `-f`、`--env-file`、project 名称和数据卷；明确停止宽限期，观察正常退出，不直接照搬默认 `docker stop`，只操作应用服务。
7. 同一旧镜像曾经过网页升级时，直接 pull/recreate 会保留升级程序。维护窗口内按私库当前指引停止应用，再用该服务的临时维护容器仅清除 `/app/data/bin/.image-seed.sha256`，强制重建应用。热回滚则只在独立目标副本中处理这个标记，不停当前服务。不要删除 `/app/data`、卷或数据库。

执行线上操作前检查已有明确授权。用户明确说“线上先别动”时，交付本次成果并等待其后续指示，不主动催促上线。用户已提出部署但尚未批准具体切换时，先完成可审阅准备，再以目标PK版本、涉及服务、备份和回退方式请求最后确认；不反复询问已批准的同一操作。
